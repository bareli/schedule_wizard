## Summary

Anyone holding the webhook URL could call it without limit and re-run the same zone repeatedly.

Filed as an issue only; the issue body and the fixer's handback are the source of truth. This record carries the verification verdict.

## Verdict (2026-10-01, qa-security-expert, fresh finder role, fixed build on 8170)

**PASS.** Instance proven to hold the fix (get_state options carry the new keys; the 429 behaviour itself was observed).

- Duplicate: run 5 min twice within 2 s: first 200, second 200 with duplicate true; variants " RUN ", upper-case entity id, "5" and 5.0 minutes all duplicate:true. History: one started row, no extra start. Different minutes (6) is deliberately not a repeat and superseded the first run, as documented. Another zone is independent. stop then stop (variant "stop ") within 2 s: second duplicate:true; after 2.2 s a stop goes through again.
- Rate limit: after a 62 s quiet period, 30 calls with an unknown zone (404 each), then a valid run, a bad action and a run on another zone all returned 429 with Retry-After 60; no zone switched, history delta 0. The window recovers: a valid run returned 200 after about 60 s.
- Not bypassed by case/space of action, entity case, other zones (one bucket per entry). Residual, by design: alternating minutes avoids the 2 s de-dup but is bounded by the 30/min limit.

Evidence: request and response text only. Redacted: webhook id and access tokens. Screenshot: Evidence unavailable, not an interface defect.
