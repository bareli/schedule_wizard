## Summary

schedule_wizard/get_state is not admin-gated (the panel is registered with require_admin=False) and returns webhook_id, options.notify_targets and notify_services (mobile_app_<device> names). The webhook id is generated once with secrets.token_hex(16) (128 bits, entropy adequate) and there is no rotate action, so a leaked URL stays valid until the config entry is removed. With SEC-001 the leaked id opens any switch, light or cover. Context: HA lets non-admin users call services anyway, so the practical gain is a credential that outlives the account and works without a token.

## Steps to reproduce

As qa_user (non-admin, valid token): WS {"type":"schedule_wizard/get_state"} -> success true; result.webhook_id present, 32 chars (value redacted); result.options contains notify_targets.
Control: same user, schedule_wizard/update_options -> error "unauthorized" (admin gate works).

## Expected

webhook_id and notify targets returned to admins only; an admin rotate action exists.

## Actual

Returned to non-admin users; no rotation path.

## Relevant files

__init__.py:393-543 (_ws_get_state, webhook_id near line 541), 360 (require_admin=False), 618-621 (id generated once); www/panel.js:2869.

## Fix prompt

In _ws_get_state blank webhook_id and strip notify_targets when not connection.user.is_admin. Add an admin-only WS command schedule_wizard/rotate_webhook (unregister old id, new token_hex(16), update entry.data, re-register) and a Rotate button beside the URL in Settings, with all 17 languages in sync (tests/test_i18n.py). Verify: non-admin get_state has no webhook_id; admin still sees and copies it; after rotation the old id gets an empty 200 and the new one works.

Evidence: request and response text above. Redacted: webhook id (shown as WEBHOOK_ID) and access tokens (never recorded). Screenshot: Evidence unavailable, not an interface defect.

## Handback: SEC-002 (#35)

**Fix:**
- `schedule_wizard/get_state` returns `webhook_id: ""` and leaves `notify_targets` out of `options` when `connection.user.is_admin` is false. It filters a copy, so the shared runtime options are unchanged.
- New WS command `schedule_wizard/rotate_webhook` (`require_admin`): it unregisters the old id, registers a new `secrets.token_hex(16)` with the same handler, stores it in `entry.data["webhook_id"]` (so it survives restarts) and returns `{"webhook_id": "<new>"}`.
- Panel, Settings → More options → Webhook:
  - admins get a **New URL** button next to **Copy URL**. It asks for confirmation, then updates the URL field in place and shows the toast "New webhook URL ready...".
  - non-admins see "Only administrators can see the webhook URL." instead of the URL.
  - the hint no longer says to remove and re-add the integration.
- The 5 new strings and the rewritten hint are in all 17 languages (`tests/test_i18n.py` passes).

**Verification recipe:**
- Accounts: qa_user (non-admin) and qa_admin, on `http://127.0.0.1:8170`.
- Steps and expected results:
  1. As qa_user, WS `{"type":"schedule_wizard/get_state"}` gives `success: true` with `result.webhook_id == ""`, and `result.options` has no `notify_targets` key.
  2. As qa_user, open `/schedule-wizard`, then Settings → More options → Webhook. There is no URL field, and the text "Only administrators can see the webhook URL." is shown.
  3. As qa_user, WS `{"type":"schedule_wizard/rotate_webhook"}` gives error `unauthorized`.
  4. As qa_admin, `get_state` gives `webhook_id` with 32 hex characters (OLD). In the same panel section the URL and the **Copy URL** and **New URL** buttons are shown.
  5. As qa_admin, click **New URL** and confirm. The URL field changes to a new id (NEW) and a toast appears.
  6. With zone_front registered, `POST /api/webhook/OLD` gives HA's empty 200 and nothing switches. `POST /api/webhook/NEW` with `{"entity_id":"input_boolean.zone_front","duration_minutes":1}` gives `200 ok`.
  7. After an HA restart, `get_state` still gives NEW.
- Before (baseline e30fa88): step 1 returned the real 32-character `webhook_id` and `notify_targets`, and step 3 failed with `unknown_command`. There was no way to rotate the id.
- UI: this change adds UI (a button and a hint); it does not fix an interface defect, and the finder filed no "before" image ("not an interface defect"). Screenshot unavailable: no instance with the fix was running for the fixer, and the brief forbids restarting the standing instance.
