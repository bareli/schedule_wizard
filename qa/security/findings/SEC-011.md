## Summary

`async_apply_tip` (scheduler.py ~2344) for kind `heat` does not require a current tip: it only checks the day is not in the past, then calls `store.async_set_boost` for that day. The `apply_tip` service regex accepts any `heat:YYYY-MM-DD`. A non-admin user can therefore (a) overwrite the single stored boost (e.g. a 14-day +30 % the owner set) with a one-day boost on a far-future day, silently cancelling it (`changed: 0` returned), and (b) trigger an unhandled `OverflowError: date value out of range` (HTTP 500, traceback in the log) with `heat:9999-12-31`. Same OverflowError with `set_boost start_date: 9999-12-31`. No storage growth (one boost record), no data disclosure.

## Steps to reproduce

As qa_user: POST /api/services/schedule_wizard/apply_tip {"tip_id":"heat:2099-12-31"} -> 200 {"changed":0}; get_state boost is now {from: 2099-12-31, until: +1 day}, replacing the previous boost. {"tip_id":"heat:9999-12-31"} -> 500. set_boost {percent:50, days:14, start_date:"9999-12-31"} -> 500.

## Expected

heat applies only when a current heat tip exists for that day (like rain/frost, which raise "nothing to change"); dates bounded to today..today+NEXT_RUN_DAYS like set_override; no unhandled exception.

## Actual

See Summary. Note the mobile-app action path (`_on_tip_action`) has the same behaviour, but it needs an event on the bus.

## Fix

In `async_apply_tip`: `if tip is None: raise ValueError("nothing to change")` for heat too (drop the `else self.boost_pct_option()` fallback), or bound `day_d <= today + 1`. In `_svc_set_boost`: reject `start_date > today + NEXT_RUN_DAYS`.
