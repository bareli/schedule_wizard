## Summary

`_async_try_pending_close` saves `pending_closes` without the entry before it writes the run's end row (`_async_record_end`). If Home Assistant stops in that window (0-20 ms, while the save is awaited) the stored data has neither the pending close nor the `completed` row, so the run's end is lost. The valve itself is closed.

## Steps to reproduce

Source-level, reproduced by the regression test: a pending close completes, and every write of the store is snapshotted; one snapshot has no pending close and no end row.

## Expected

The end row is recorded first and saved in the same write that removes the pending close (never a lost row, never a double row, never a valve left open).

## Actual

The write that drops the pending close has history `['started']` only; the end row follows in a later delayed save.

## Evidence

Not an interface defect; the failing test is the evidence.

## Relevant files

custom_components/schedule_wizard/scheduler.py (`_async_try_pending_close`), storage.py

## Handback (qa-developer, 2026-10-01)

Fix commits `509425d` on `fix/v0.15.0-polish`. Full handback with recipe and environment: issue #87.

**Fix** (commit `509425d`, `scheduler.py` `_async_try_pending_close`, `storage.py`): when a pending close is done, the run's end row is recorded first (in memory, no await in between), then the entry is removed with the new `store.async_drop_pending_close(entity_id)`, whose save writes both together. It removes only that entity's entry and also works while Home Assistant is stopping (the old path skipped the save while stopping, which left the entry stored next to a written row: a second row on the next start). The valve close itself is unchanged and happens before either write.
