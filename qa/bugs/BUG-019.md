## Summary

Record written by qa-developer from issue #80 (the finder filed the issue without a record). At the end of a run Schedule Wizard calls `switch.turn_off`; when the valve is `unavailable` at that moment HA refuses the call ("Referenced entities ... are missing or not currently available", log warning only). The run is still recorded `completed` and dropped, so when the valve comes back `on` nothing closes it. Panel shows "All good", zone Off. Always-in-scope rule: never leave a valve open.

## Steps to reproduce

Start a 1-minute run on a zone whose switch goes `unavailable` before the run ends (e.g. a Zigbee / Wi-Fi valve dropping out), let it come back `on` after the end. No restart needed. How to fake an unavailable valve: `qa/knowledge/live-restart-checks.md`.

## Expected

A close sent to an unavailable valve is not done. Keep a pending close (persisted across restart), wait for the valve's first real state and close it; record the close when it actually happens. Applies to restored runs too (remaining part of #54).

## Actual

`completed` recorded at the end, run dropped, valve back `on` and never closed.

![valve open after completed](https://github.com/bareli/schedule_wizard/blob/main/qa/evidence/BUG-015-valve-open-after-completed-verify.png?raw=1)

## Root cause

`scheduler.py` `_call_service_off` swallowed every outcome: HA drops calls to unavailable entities without raising, and exceptions were only logged. `_async_complete` then recorded the run as done regardless.

## Regression test

`tests/test_unavailable_close.py`.

## Handback (qa-developer, 2026-10-01)

Fixed in `6466e9b` on branch `fix/v0.15.0-unavailable-close` (not merged, not pushed; worktree `C:/Users/barel/AppData/Local/Temp/claude/D--Code-home-assistant-extensions-good-days/f3802ecc-2b66-432d-963d-f0b1f5d18979/scratchpad/wt-v15-close`). Baseline: `feature/v0.15.0` @ `ebd0b8a`. Same commit also covers the reopened #54.

**What changed** (`scheduler.py`, `storage.py`): a close that does not reach the valve is no longer treated as done.
- `_call_service_off` now returns whether the close was delivered: `False` when the entity is missing, `unknown` or `unavailable` (HA would drop the call with only the "Referenced entities ... are missing or not currently available" warning), when the call raises, or when the entity went unavailable during the call.
- Not delivered: the valve gets a **pending close**, persisted in the store as `pending_closes` (survives a restart), plus a state listener with no time limit. On the valve's next real state: `on` (or `open`/`opening`) -> close it; `off`/closed -> trusted as closed (owner policy), no command. The history row (`completed`, `cancelled`, `expired_during_downtime`...), the `schedule_wizard_valve_ended` event and the notification are written **when the close is done**, not before.
- The run itself leaves `active` at its end as before, so the master valve can close and a plan goes on to its next zone; a new run on the same valve replaces its pending close (its row is written then).
- A close refused by a valve that is still available (device error) is retried every 60 s until it works.
- Paths covered: timer end (the auto-close), Stop, Stop all, plan steps (sequential and interleaved), soak chunks, cycle resume after restart, runs that expired during the downtime, a run cancelled while starting / failed to open, Stop on an idle zone, and the master valve (normal close and flow "stop all").
- #54: every restored run is now watched, whatever its state at load. A stale restored `on` that turns `unavailable` a moment later puts the run in the same "wait for the first real state" mode as a valve unavailable at load: still unavailable at the end -> closed as soon as it reports `on`, one `completed` row; reports `off` -> `cancelled_during_downtime`.

Not changed: panel / card show a pending close as not running (no UI for it in this fix); the state is visible in `.storage/schedule_wizard.data` -> `pending_closes` and in the log line `close of <entity> not delivered: it will be closed when it reports a state`.
