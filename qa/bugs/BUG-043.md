# BUG-043 A scheduled run waiting for a free slot is silently dropped by an HA restart

| | |

| Model | opus |

## Summary

`Scheduler._queue` lives only in memory. A run waiting its turn when HA restarts never runs after the restart and leaves no history row or skip event, unlike the 3 h give-up (which records `skipped_overlap`). PROJECT.md "Always in scope": schedules fire across HA restarts.

## Steps to reproduce

1. Settings: Zones at once = 1.
2. Water now Front lawn 5 min (06:02:13).
3. Schedule "QA queue restart" Herb bed Fri 06:05, 2 min. At 06:05:17 `get_state.queue` lists it.
4. Restart HA (06:05:17; forced kill via restart_ha.sh).

## Expected

After the restart the waiting run is restored (or at least recorded as skipped with a reason) and starts when Front lawn ends.

## Actual

After restart: Front lawn restored and ended 06:07:13; `queue` = []; Herb bed never turned on; no history row or event for schedule 4de23dbe613f. Code shows the same for a graceful stop (`_async_wait_turn` returns False on `_stopping` without recording). Product call needed on restore vs record, hence model:opus.

## Verification

Verdict: VERIFIED (2026-10-09, dev 8180 on 89195a1, about 25 min).
- Zones at once = 1, Front lawn 10 min running, two scheduled runs (Back garden, Herb bed) queued at 06:51:00. Graceful HA restart: after boot get_state.queue listed both with the original since stamp, Front lawn restored. Front ended 06:59:21; Back garden started 06:59:25, Herb bed 07:00:25 (oldest first, one slot), history rows "started" present.
- Forced kill (restart_ha.sh) with one queued run: queue entry restored and it started (the manual Front lawn run was recorded cancelled_during_downtime, because the test input_boolean lost its state on a kill; unrelated to the queue fix).
