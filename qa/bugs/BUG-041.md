# BUG-041 Forged or arbitrary-day heat tip action replaces the user's active boost

| | |
|---|---|
| Type | Bug |
| Severity | medium |
| Status | Verified |
| Feature | Weather tips, notification actions / apply_tip |
| Test case | TIP-04 |
| Environment | dev (8180), HA 2026.9, feature/v0.16.0 @ b58a4b0 |
| Detected | 2026-10-09 |
| Model | sonnet |

## Summary

`Scheduler.async_apply_tip` raises "nothing to change" for a rain / frost tip that is not current, but for `heat` it calls `store.async_set_boost` even when no current tip exists (`tip is None`). The store holds one boost, so any heat action for any future date (forged `mobile_app_notification_action`, or `schedule_wizard.apply_tip` from any signed-in user) overwrites the user's running or planned boost.

## Steps to reproduce

1. Boost +30 % planned for 2026-10-10 (`get_state.boost` = {pct 30, from 1791590400, until 1791676800}).
2. WS `fire_event` `mobile_app_notification_action` with `{"action":"SCHEDULE_WIZARD_TIP_HEAT_20261225"}`.
3. Read `get_state.boost`.
4. Again as non-admin `qa_user`: `call_service schedule_wizard.apply_tip {"tip_id":"heat:2026-12-24"}`.

## Expected

TIP-04: a forged / non-current action changes nothing (same as rain/frost: "nothing to change"). The response for step 4 should be an error.

## Actual

Step 3: boost = {pct 30, from 1798156800 (2026-12-25), until 1798243200}; the 10-10 boost is gone. Step 4: response `{"changed": 0}` and boost replaced again (from 1798070400, 2026-12-24). Reproduced twice. Malformed actions (bad date, unknown kind, short stamp) were correctly ignored.

## Likely root cause

scheduler.py `async_apply_tip`: the `if kind == "heat"` branch does not require `tip` to be non-None. Fix: raise ValueError("nothing to change") when `tip is None` for heat too. (Separately worth a product call: applying a valid heat tip also replaces a longer multi-day boost.)
