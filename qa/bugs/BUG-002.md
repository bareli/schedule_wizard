Declared standard: `qa/PROJECT.md` names none, so WCAG 2.1 AA is used (stated assumption). Tooling: Chromium 153 driven by Playwright 1.63.0, real keyboard events, DOM focus and the Chromium accessibility tree (`ariaSnapshot`). **No real screen reader was available**; nothing below claims what NVDA, JAWS or VoiceOver announce.

## Summary

The panel rebuilds its whole DOM (`app.innerHTML = ""`) on a 5 s timer and after every service call. The element that has focus is destroyed, so focus drops to `<body>`. A keyboard or screen-reader user loses their place at most 5 s after each Tab press, and after every button they activate. The Lovelace card does the same. Only text inputs, textareas and selects are protected, and the Settings tab is exempt.

## Steps to reproduce

1. Log in as `qa_admin`, open `/schedule-wizard` with at least one zone and a plan registered.
2. Press Tab to a tab button (for example Zones) or any control on Home (Water now, the "More time" stepper) and stop pressing keys.
3. Wait 7 s. Read the focused element (`document.activeElement`, followed through shadow roots).
4. Press Enter on the focused tab; press Enter on Water now.
5. Card: mount `schedule-wizard-card`, focus its Run button, wait 6.5 s.

## Expected

Focus stays on the control the user put it on until the user moves it (2.4.3). Updating a countdown or status must not move or destroy focus. Source: WCAG 2.1 2.4.3; the code already tries this for inputs (`_updateInPlace`), so the intent exists.

## Actual

| Step | Focus after |
|---|---|
| Focus Zones tab, idle 7.5 s | `BODY` |
| Enter on that tab | nothing happens (focus is on body), tab not activated |
| Focus Water now, idle 7.5 s | `BODY` |
| Press Enter on Water now | zone starts, focus `BODY` |
| Press "More time" (value changes, focus kept), idle 7.5 s | `BODY` |
| Card: focus Run, idle 6.5 s | `BODY` |
| Settings tab | not affected (refresh returns early) |

The next Tab from `BODY` goes to the Home Assistant sidebar toggle, so the user restarts the whole page.

## Evidence

Evidence unavailable as an image: focus loss is a state, a still picture does not show it. The sequence above is from Playwright runs on 2026-10-01 (keys Tab / Enter, `document.activeElement` read through shadow roots before and after). Code: `panel.js` `_refresh` (L648-669, `setInterval` 5000 at L645) calls `_render()` (L740-775) unless a text field is focused; `card.js` `_refresh` (L231-245) and `_render` (L279-282) do the same.

## Likely root cause

`_render()` and the card's `_render()` replace all nodes; only inputs are exempt from the 5 s refresh. A control that was focused is simply removed. Likely, not proven by a patch.

## Relevant files

`custom_components/schedule_wizard/www/panel.js` (`_refresh`, `_render`, `_callService`, tab onClick), `www/card.js` (`_refresh`, `_render`).

## Recommended remediation

Before re-rendering, remember the focused control by a stable key (a `data-focus-key` from entity id and action) and re-focus its replacement afterwards; or skip the full render when only live numbers changed (use `_updateInPlace` for countdowns, progress and status text) and re-render only when the data structure changed. After an action (Water now, Stop, tab change) move focus deliberately: to the same logical control or to the new panel.

## Regression test

A11Y-01: Playwright check that after 6 s focus is unchanged on Home, Zones and Programs, and on the card. A pytest unit test cannot see focus; a markup test would pin only part of the fix.
