## Summary

Since 0.13 Schedule Wizard deliberately leaves valves open during an HA shutdown "so the running zone finishes its time" and restores the run on start. The restore reads the valve's state **once**, at Schedule Wizard setup. If the valve's own integration (Z-Wave JS, ZHA, MQTT, ESPHome, Shelly...) has not loaded yet, the state is missing, `unknown` or `unavailable`; the run is then recorded `cancelled_during_downtime` (or `expired_during_downtime`) and dropped with no close command and no timer. When the valve's integration comes up a few seconds later, the valve reports `on` and nothing ever turns it off. That is the "never leave a valve open" rule in `qa/PROJECT.md` *Always in scope*.

## Steps to reproduce

Test harness (reproduced twice, 2 of 2 cases fail):

1. Persist an active run for `switch.qa_late_valve` ending in 120 s (`hass_storage["schedule_wizard.data"]["active_runs"]`).
2. Case A: no state for the switch at setup (integration not loaded). Case B: state `unavailable` at setup.
3. Set up Schedule Wizard; then set the switch state to `on` (its integration finished loading, valve still physically open).
4. Advance time 130 s; check whether `switch.turn_off` was called.

The test file used is kept in the session scratchpad as `qe_test_restore.py`; it was removed from `tests/` after the run.

## Expected

The valve is closed at its original `ends_at` (or immediately if that has passed) once its entity is available, and history gets one terminal row. Source: `qa/PROJECT.md` *Always in scope* ("close their valve after the duration, including across HA restarts ... never leave a valve open"); CHANGELOG 0.13.0 ("the running zone finishes its time").

## Actual

```
AssertionError: valve never turned off; history=['cancelled_during_downtime']
2 failed, 1 warning in 1.46s
```

No `turn_off` call in either case; the run is gone from `active` and `active_runs`, so the panel shows nothing running while the valve is open.

## Evidence

pytest output above (HA 2026.9 venv `venv314`). The existing `test_restore_active_run_after_restart` only covers a valve that is already `on` at setup. Evidence unavailable for a live restart: the brief reserves HA restarts for the orchestrator.

The 8170 zones are `input_boolean`s, which restore `on` before custom integrations load, so a plain restart there cannot show it. Live check that would (orchestrator, one restart): add a `template:` switch `switch.qa_late` backed by an input_boolean, with an `availability` template that is false for the first 60 s after start (uptime sensor); register it as a zone, start a 3-minute run, restart HA, and confirm 4 minutes later that the backing input_boolean is still `on` and history says `cancelled_during_downtime`.

## Likely root cause

Proven in the harness: `scheduler.py` `_async_restore_active_runs` treats any state outside `ON_STATES` (including `None`, `unknown`, `unavailable`) as "valve was closed during downtime" and drops the run; the `remaining <= 0` branch only calls `_call_service_off` when the state is already `on`. Nothing re-checks later, and `manifest.json` has no `after_dependencies` that would order Schedule Wizard after valve integrations (and it cannot list them all).

## Relevant files

- `custom_components/schedule_wizard/scheduler.py` (`_async_restore_active_runs`, `ON_STATES`, `UNAVAILABLE_STATES`)
- `tests/test_scheduler.py` (`test_restore_active_run_after_restart`)

## Recommended remediation

Product call on the exact policy (hence opus). Shape: when the valve state is missing / `unknown` / `unavailable` at restore, keep the run (timer to `ends_at`), and listen for the entity's first real state; at `ends_at` (or on first availability if already past) send the close command regardless of the state seen at setup. Record `cancelled_during_downtime` only when the entity is available and reports off. Same for the `expired` branch: always send close when the run expired, not only when the state is `on`.
